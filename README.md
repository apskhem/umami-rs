# umami-rs server

A headless Rust backend that is a drop-in replacement for [Umami](https://umami.is)
**v3.4.1** on PostgreSQL: same database schema, same JSON API, so existing Umami
databases, the official tracker script and the official dashboard work against it.

## Layout

| Crate | Purpose |
|---|---|
| `umami-db` | Connection handling and the migrator. `migrations/` is a verbatim copy of upstream's Prisma migrations, applied with Prisma's `_prisma_migrations` bookkeeping so upstream and umami-rs can migrate the same database interchangeably. |
| `umami-server` | The axum HTTP server (`umami-server` binary). |
| `crate-ua-rules` | User-agent classification (bots, browser, OS, device type), ported from the JS libraries upstream uses. Standalone: depends only on `regex` and `fancy-regex`. |
| `parity` | Differential tests that run upstream Umami and umami-rs side by side and compare their responses and database rows. |
| `tools/tracker` | Fetches upstream's built tracker script (`umami-server/assets/script.js`) from its release image. |
| `tools/ua-rules` | Generates `crate-ua-rules`' rule tables and parity fixtures from the JS libraries upstream uses. |

## Running

```sh
docker compose up -d          # local Postgres
cp .env.example .env
cargo run -p umami-server
curl localhost:3000/api/heartbeat   # {"ok":true}
```

On startup the server checks the Postgres version and applies pending migrations, as
upstream's `check-db` script does. A fresh database gets upstream's default login,
`admin` / `umami`.

### Docker

The `Dockerfile` builds a static (musl) binary into a `scratch` image of about
13 MB: no shell or libc, running as UID 65534, with `umami-server healthcheck` as
its healthcheck. Mount a GeoLite2 database at `/app/geo` for geolocation, as with
upstream's image.

```sh
docker build -t umami-rs .
docker run -p 3000:3000 -e DATABASE_URL=... -e APP_SECRET=... umami-rs
```

## Event collection

`POST /api/send` and `POST /api/batch` accept the official tracker's payloads and
write the same rows upstream does: session and visit IDs, cache tokens, UTM and
click-ID parsing, custom event data, revenue, `identify` and web-vitals events.

- **Geolocation** comes from CDN headers (Cloudflare, Vercel, CloudFront, EdgeOne)
  or a MaxMind GeoLite2 City database at `geo/GeoLite2-City.mmdb` (or
  `GEOLITE_DB_PATH`). Without a database the server still runs and relies on headers.
- **User agents** are classified by `crate-ua-rules`, Rust ports of `detect-browser`,
  `isbot` and `ua-parser-js` generated by `tools/ua-rules` and tested against those libraries
  on ~2,300 real user agents. Device types come from ua-parser-js 1.x (MIT): upstream
  uses 2.x, which is AGPL-licensed, and the two disagree on under 1% of the corpus.
- Session and visit periods are computed in UTC (upstream uses the server's time
  zone, which is UTC in its Docker image).

To update the user-agent rules after an upstream bump, change the versions in
`tools/ua-rules/package.json`, then:

```sh
cd tools/ua-rules && npm ci --ignore-scripts && npm run generate && npm run fixtures
```

## Authentication

Login (`/api/auth/*`), `/api/me`, `/api/config`, password changes, API keys
(`/api/me/api-keys`) and two-factor authentication (`/api/2fa/*` and the admin
policies under `/api/admin/**/2fa`) behave as upstream's.

- Session tokens use upstream's format (an encrypted JWT keyed by `APP_SECRET`,
  bound to the password), so a token issued by either server is accepted by the
  other, and changing a password signs the user out of both.
- Two-factor authentication needs `TWO_FACTOR_ENCRYPTION_KEY` and is compatible with
  upstream's stored secrets, backup codes, lockout (5 failures, 15 minutes) and
  replay protection.
- Sessions are stateless: Redis-backed sessions (`REDIS_URL`) are not supported.
  `/api/auth/sso` still works (upstream fails without Redis): it returns a session
  token that expires after a day, which upstream also accepts. Without a session
  store, logging out cannot revoke a token, as with upstream without Redis.

Differences from upstream: login returns the username as stored, not as typed;
2FA codes from the adjacent 30-second steps are also accepted (RFC 6238's
clock-drift tolerance; upstream accepts only the current step); the 2FA setup QR
code is an SVG rather than a PNG (same code); a non-numeric 2FA code is rejected as
invalid (upstream errors with 500); and malformed IDs in paths return 404
(upstream errors with 500).

## Users, teams and websites

User administration (`/api/users/*`, `/api/admin/users`), teams and their members
(`/api/teams/*`, `/api/me/teams`, `/api/admin/teams`) and website management
(`/api/websites`, `/api/websites/{id}` with `reset` and `transfer`, `/api/me/websites`,
`/api/admin/websites`) behave as upstream's, with the same roles and permissions,
paging, sorting and search.

Differences from upstream, where upstream fails or leaves inconsistent data:

- **Deleting** a team also deletes its websites, as upstream's UI warns it will
  (upstream keeps them without a team). Deleting a user deletes everything their
  websites hold, the teams they own with those teams' websites, links, pixels and
  boards, and their websites' share links. Upstream refuses with a 500 while the
  websites have revenue, segments, annotations, replays or heatmap data, and
  otherwise leaves those rows behind.
- **Taken IDs, usernames (including a deleted user's), share IDs and access codes**
  return 400 where upstream fails with a 500. Creating or updating a website with a
  taken share ID changes nothing (upstream creates or updates the website first).
- **Users and teams that do not exist** cannot be made team members, team owners,
  website teams or transfer targets (404); upstream stores the dangling IDs.
- **Lists** are always in a stable order, ties broken by ID, so pages never
  overlap. Lists upstream leaves unordered (a user's teams, a team's websites and
  members) are ordered by name or join time. Search matches `%` and `_` literally,
  where upstream treats them as wildcards.
- **Missing records** (deleting, resetting or transferring something that does not
  exist, or a malformed ID) return 404 where upstream fails with a 500, and routes
  that need a signed-in user return 401 to share-link visitors.

## Share links and segments

Share links (`/api/websites/{id}/shares`, `/api/share`, `/api/share/id/{shareId}`)
are created, listed, updated and deleted as upstream's, for websites, links, pixels
and boards. Opening one (`GET /api/share/{slug}`, no sign-in) returns what it shares
and a share token in upstream's format, so tokens from either server work on both.
A board's link shares the websites, pixels and links on the board that its owner
may share. Saved segments and cohorts (`/api/websites/{id}/segments` and
`/api/websites/{id}/segments/{segmentId}`) are stored as upstream stores them (only
the known parameters), and share links can read them unless they disable filters.

Differences from upstream:

- **Taken slugs** return 400 where upstream fails with a 500.
- **Shares that could never be opened** are refused: a share of an entity that
  does not exist (404) or whose `shareType` is not the entity's type (400).
  Upstream stores both. Likewise, admins cannot save a segment, or create a website
  share, for a website that does not exist (404).
- **Missing records** (a share or segment that does not exist, or a malformed ID)
  return 404 where upstream fails with a 500.
- **The segment list** is oldest first, ties broken by ID; upstream leaves it
  unordered. As upstream, it ignores paging parameters and returns the first 20.
- **White labels** are not attached to opened share links: upstream keeps them only
  in Redis, which umami-rs does not use (as upstream without Redis).

## Links and pixels

Short links and tracking pixels (`/api/links` and `/api/pixels`, each with `/{id}`,
`/{id}/shares` and `/charts`, and `/api/teams/{id}/links` and `/pixels`) are created,
listed, updated, shared and deleted as upstream's, with the permissions of websites.
Visiting a link (`GET /q/{slug}`) records a link event and redirects to the link's
URL (307); loading a pixel (`GET /p/{slug}`) records a pixel event and returns
upstream's 1×1 GIF. Visits go through the same collection as `/api/send` (sessions,
geolocation, bot filtering, `IGNORE_IP`), and the visitor is redirected or served
the image whether or not the visit is recorded.

Differences from upstream:

- **Visits record the request's `Host` as the hostname**; upstream records its own
  listening address (`0.0.0.0` in its Docker image).
- **Deleting** a link or pixel also deletes its share links and collected events,
  as does deleting the user or team that owns it; upstream keeps both.
- **Taken IDs and slugs** return 400 on create where upstream fails with a 500, as
  do malformed team IDs; a team that does not exist is a 404 (upstream stores it).
- **Missing records** (an admin updating, deleting or sharing one that does not
  exist, or a malformed ID) return 404 where upstream fails with a 500 or, for
  shares, stores a share of nothing.
- **Lists** are ordered by name unless sorted, ties broken by ID; upstream leaves
  them unordered. Soft-deleted links and pixels are left out of every list
  (upstream shows them in team lists and a user's pixels).
- **Charts** count the local half-days (00:00 and 12:00) that the range covers.
  Upstream labels its buckets from the range's start, so a `startAt` between
  half-days, or a daylight saving change in the range, leaves the later buckets
  at zero.
- **A link whose URL cannot be parsed** returns 400 without recording the visit;
  upstream records it, then fails with a 500.

## Boards

Boards (`/api/boards`, `/api/boards/{id}` with `clone` and `shares`,
`/api/teams/{id}/boards`) and each user's own dashboard (`/api/dashboard`, a board
whose ID is the user's) are created, listed, updated, cloned, shared and deleted as
upstream's. As upstream, a board may only show websites, pixels and links its
creator can view, and funnel and goal components must name a saved report of that
type on their website; cloning drops report references that no longer hold.
`/api/websites/charts` serves the website list's sparklines, like the link and
pixel ones.

Differences from upstream:

- **Deleting** a board also deletes its share links; upstream keeps them.
- **Layouts upstream cannot read** (`rows`, or a row's `columns`, that are not
  lists of objects) and report references that are not UUIDs return 400 where
  upstream fails with a 500.
- **A first dashboard save** without a name or description saves them empty;
  upstream fails with a 500.
- **Missing records** (an admin renaming, deleting or sharing a board that does
  not exist, or a malformed ID) return 404 where upstream fails with a 500 or, for
  shares, stores a share of nothing. A team that does not exist is a 404 when
  creating a board (upstream stores it).
- **Lists** are ordered by name unless sorted, ties broken by ID; upstream leaves
  them unordered.

## Analytics

The website dashboard's queries under `/api/websites/{id}`: `stats`, `pageviews`,
`metrics` and `metrics/expanded` (every dimension, plus channels), `active`,
`daterange` and `values`; `events` (list, `series`, `stats`); `sessions` (list,
`stats`, `weekly`, and each session with its `activity` and `properties`, or
`DELETE` to remove it); and `/api/realtime/{id}`. They take upstream's parameters: the date range,
`timezone`, `unit` and `compare`, column filters (`browser=neq.chrome`, `path=c./blog`,
`match=any`), event- and session-data filters (`epf0`, `spf0`), segments, cohorts and
`excludeBounce`. Share links see only the sections they enable. Results match
upstream's for the same data, including its JSON types (sums are strings, as Prisma
returns them).

Differences from upstream:

- Lists break ties in a fixed order (by value, or event ID for events at the same
  instant), which upstream leaves to the database, so pages never overlap.
- The sessions list has one row per session, with its latest hostname; upstream
  lists (and counts) a session once per hostname it was seen on.
- `startDate`/`endDate` work as an alternative to `startAt`/`endAt` (upstream fails
  with a 500), and `excludeBounce=false` does not exclude bounces (upstream treats any
  value as true).
- These return 400 where upstream fails with a 500: a negative `limit` or `offset`
  (on metrics and event series),
  an unknown segment or cohort, a filter operator a column cannot use (`s.`, `gt.`),
  or an invalid regex or date in a filter. A malformed website ID is a 404.
- Time zones are those Postgres knows (upstream checks with JavaScript's `Intl`,
  which also accepts offsets such as `+05:30`).

## Tracker script

`/script.js` serves upstream's tracker exactly as the v3.4.1 release image ships it,
with the same caching and CORS headers; `TRACKER_SCRIPT_NAME` adds alias paths and
`COLLECT_API_ENDPOINT` re-points the script, as upstream does at startup. Embed it
as with upstream:

```html
<script defer src="https://analytics.example.com/script.js" data-website-id="..."></script>
```

To track a newer upstream release, run `python3 tools/tracker/fetch.py <version>`
and update `SCRIPT_SHA256` in `umami-server/src/tracker.rs`.

Not supported: `TRACKER_SCRIPT_URL` (proxying the script from elsewhere),
`COLLECT_API_HOST` (a build-time option upstream; use `data-host-url` instead) and
the session-replay `recorder.js`.

## Configuration

Environment variables follow upstream where an equivalent exists; see `.env.example`.
`HOST` replaces upstream's `HOSTNAME`, which Docker sets to the container ID.

## Tests

```sh
cargo test                                   # unit + HTTP tests, no database needed
TEST_DATABASE_URL=postgresql://umami:umami@localhost:5432/umami \
  cargo test -- --include-ignored            # also run database tests
```

### Parity with upstream

`parity/compose.yaml` runs upstream's official 3.4.1 image and umami-rs (built from
this repo) on one Postgres, each with its own database, plus each server on the
database the other migrated. The parity tests send both the same requests and assert
identical responses and rows, an identical schema, and that each server accepts the
other's migrations. A browser test also runs the real tracker in headless Chrome
against both servers (skipped if no Chrome or Chromium is found; set `PARITY_CHROME`
to choose one):

```sh
docker compose -f parity/compose.yaml up -d --build --wait
cargo test -p umami-parity -- --ignored
docker compose -f parity/compose.yaml down -v
```

Known, intentional differences (not exercised by the parity tests): device types
differ for under 1% of user agents (ua-parser-js 1.x vs 2.x); and in error cases
umami-rs answers 400 rather than 500 for unparseable page URLs, ignores a cache token
issued for another website, keeps impossible event-data dates as strings, and runs
without a GeoLite2 database instead of failing.
